## #169 本番反映（wrangler deploy）を GitHub Actions で実行できるようにする

- 作成: 2026-09-12
- ラベル: 分野: 自動化, 分野: インフラ

### 本文

現在、本番反映（`npx wrangler deploy`）は平野さんの手元での手作業でしか行えず、
リポジトリにもデプロイ手順の記載が無い。これを GitHub Actions から実行できるようにする。

## 背景

Claude Code のセッション環境からは **`api.cloudflare.com` がネットワークポリシーで
遮断されている**（`connect_rejected`）ため、セッション内から直接デプロイすることはできない。
API トークンを渡しても認証以前に到達できないため解決しない。同じ理由で `ryoei.pro` にも
到達できず、本番の状態を確認することもできない。

GitHub Actions の runner は外部ネットワークに出られるため、この制約を回避できる。

## 方針

- ワークフローを1本追加し、`cloudflare` ブランチへの push で自動デプロイ、
  加えて `workflow_dispatch` で手動実行もできるようにする
- 認証は GitHub のリポジトリ Secret `CLOUDFLARE_API_TOKEN`。
  **トークンはリポジトリにもセッションにも現れない**
- 第三者製の action（`cloudflare/wrangler-action` 等）は使わず、
  `npx wrangler@<版> deploy` を `run:` で直接叩く。既存の
  `regenerate-page.yml` と同じ書き方に揃え、依存を増やさないため
- 再生成ワークフローが `chore: regenerate ... via GitHub Actions` を push した場合も
  デプロイが走る。シートの更新が自動で本番へ届くようになる

## 検討したが採らなかった案

- **Cloudflare の Git 連携（Workers Builds）**: ダッシュボードで設定でき、GitHub に
  Secret を置かずに済む。一度は採用しかけたが、設定がリポジトリ外にあり、
  どういう構成で動いているかがコードから追えない点を避けた
- **セッション環境のネットワークポリシー変更**: 新しいセッションからしか有効にならず、
  トークンの置き場所も広くなる

## 1. `jpml_pros` からの25リンクが、折れ線の出ないページに着地する【確認済み】

`jpml_pros.html` は `houou_leagues.html?name=` へ **716件**リンクしている。そのうち **25件**は `houou_leagues_data.json` に存在しない選手を指している。

```
jpml_pros.html:      houou_leagues?name= リンク 716件 / 折れ線が出ない先 25件
houou_leagues.html:  houou_leagues?name= リンク 691件 / 折れ線が出ない先   0件
```

該当例（25名の一部）:

```
中村朝海, 中村泰詩, 中馬雄志, 久野智子, 内山藤次朗, 和田聡一隆,
大島琉雅, 大崎菜緒, 安井駿, 安部みゆ, 寺下達規, 小倉慶一郎,
小川慈瑛, 小松崎舞, 小松心音, ...
```

### 原因

716 = 691 + 25 で、`generate_houou_leagues.py` の出力にぴったり一致する。

> 鳳凰シートにヒットしない選手を25名スキップしました。

両ページは同じ基準（「プロ」シートの Y列="Y" かつ Q列が非NULL）で716名を選んでいるが、**`houou_leagues` だけが「鳳凰シートに実データがある」という追加条件で25名を落としている。** `jpml_pros` 側にはその条件がないため、リンクだけが残る。

`generate_houou_leagues.py` はこのスキップを意図的に行っている（「選んでも折れ線が出ない項目を作らないため」）。セレクトボックスからは正しく消えているが、`jpml_pros` からの導線は残っている、という非対称。

### 着地したときの挙動

`?name=` の値が `houou_leagues_data.json` に無い場合、`leagues.js` は折れ線の `points` を空にし、凡例のラベルだけをその名前に差し替える。実機で確認した挙動:

```
?name=存在しない名前 → polyline あり / 点数 0 / 凡例ラベル「存在しない名前」
```

**積み上げ棒は出るので白紙ではないが、凡例に名前が出ているのに線が無い**という状態になる。旧Google Charts版も同じ挙動だった（`addColumn('number', search_name)` が名前を無条件に使っていた）ため、#127による退行ではない。

### 直し方の案

- (a) `jpml_pros` 側でも「鳳凰シートに実データがある」を条件に加えてリンクを出さない → 2ページの基準が揃う。ただし `generate_jpml_pros.py` が鳳凰シートを読む必要が出る
- (b) `houou_leagues` 側で25名もoptionに残す → リンクは生きるが、選んでも線が出ない項目が復活する
- (c) 折れ線が無いときに「この選手の鳳凰戦の記録はありません」と出す → どちらの基準も変えずに、着地時の体験だけ直す

**(c) が最も影響範囲が小さい。** (a) は筋が通るが生成スクリプトの依存が増える。

## 2. 選択可能な選手が88名入れ替わった【要判断・未確認部分あり】

#127 でセレクトボックスが手書き695名から自動生成691名に変わったが、**単純な4名減ではなく88名減・84名増**だった。

```
旧option 695名 → 新 691名
  選べなくなった: 88名
  新しく選べるようになった: 84名
```

選べなくなった88名には `前原雄大` が含まれる。他に `中村太一` / `石川駿` / `吉村隼人` / `水越京子` / `吉田祥子` など。

### これは想定内の可能性が高い

`generate_houou_leagues.py` のdocstringに次の記載がある。

> 現行の695名の出典は「プロ」シートとの突合でも一致率9割程度で特定できなかったため、実データを再検証した上でこの基準に切り替えた

88/695 ≒ 12.7% で「9割程度」と整合する。**手書きリストが古かったものを、正本（プロシート）に合わせ直した結果**と読める。

### ただし確認できていない点

**88名の中に、鳳凰シートに実データがあるのに選べなくなった選手がいないか。**

`generate_houou_leagues.py` は `series`（鳳凰シート全行から作る）を作った後に `option_names` で絞り、**JSONも絞った後のものを書き出している**（`data_json = {name: series[name] for name in option_names}`）。そのため生成物からは「絞られた側に鳳凰データがあったか」を判定できない。

`前原雄大` のようなベテランは鳳凰戦の出場歴があるはずで、あれば見られなくなったことになる。`?name=` 付きURLは検索流入の主力（handover.mdのSEO節）なので、インデックス済みURLが該当していると影響が出る。

### 確認方法

生成スクリプトに一時的な出力を足して、`series` にあって `option_names` に無い名前を数えるだけで分かる。

```python
dropped = [n for n in series if n not in set(option_names)]
print(f"鳳凰データがあるがoptionから除外: {len(dropped)}名", dropped[:20])
```

0名なら想定内で何もしなくてよい。1名以上なら、その選手を救うかどうかの判断が必要になる。**スプレッドシートに到達できる環境で実行してほしい。**

### 原因

```yaml
- uses: actions/checkout@v4
  with:

...

```

`HEAD^ HEAD` は最終コミット1つ分の差分。push に含まれるコミット全体の
範囲ではない。

### 対応案

push イベントが持つ範囲（`github.event.before` 〜 `github.sha`）で差分を
取る。あわせて `fetch-depth` を広げる必要がある（`0`、または範囲を賄える
深さ）。

- ブランチ新規作成時や force push 後は `github.event.before` が
  `0000000...` になる。その場合は `all` へフォールバックするなどの
  分岐が必要
- 範囲が広がるぶん対象ページが増え、実行時間が延びるケースがある

簡易案として「`scripts/lib/**` が push 範囲に含まれていたら無条件に `all`」
でも今回のケースは防げる。

毎週月曜 05:37 JST の定期実行（`all`）があるため、漏れても最大1週間で

## #132 regenerate-page.yml で workflow_dispatch の入力を run: に直接展開している

- 作成: 2026-09-11
- ラベル: 分野: 自動化, 分野: セキュリティ

### 本文

### 状況

`.github/workflows/regenerate-page.yml` の「対象ページを再生成」ステップで、
`workflow_dispatch` の入力を `run:` ブロックへ直接展開している。

```yaml
python3 scripts/regenerate.py ${{ github.event.inputs.target_page }} \
  | tee /tmp/targets.txt
```

GitHub Actions の script injection の典型パターン。`${{ }}` はシェルが起動する前に
テキストとして置換されるため、入力に `;` や `$( )` を含めると任意のコマンドが走る。

同ファイルの「変更をコミット・push」ステップにある
`git add ${{ steps.regen.outputs.files }}` も同じ形。こちらの値は
`scripts/regenerate.py` の出力（リポジトリ内のコードが決める）なので、外部入力ではない。

### 深刻度は低い

`workflow_dispatch` の実行にはリポジトリへの write 権限が必要で、
**外部から到達できる経路ではない。** すでに push できる人だけが悪用できるため、
実質的な権限昇格にならない。

ただし修正が数行で済むこと、このワークフローは `cloudflare` ブランチへ push する
権限で動いており成功すれば本番に反映されることから、直しておく。

### 対応

入力を `env:` 経由に移し、シェル側で変数として参照する。

```yaml
      - name: 対象ページを再生成
        id: regen
        env:
          TARGET_PAGE: ${{ github.event.inputs.target_page }}
        run: |
          set -o pipefail
          if [ "${{ github.event_name }}" = "workflow_dispatch" ]; then
            python3 scripts/regenerate.py $TARGET_PAGE | tee /tmp/targets.txt
          else
            ...
```

`$TARGET_PAGE` をクォートしないのは、`target_page` が
「スペース区切りで複数ページ」を受ける仕様（`scripts/regenerate.py` の
`pages` 引数が `nargs="*"`）で、単語分割を意図的に使っているため。
クォートすると `all` 以外の複数指定が1つの引数として渡り壊れる。
**クォートなしでも `env:` 経由であれば `; rm -rf` のような注入は起きない**
（シェルは展開後の値を再解釈しないため）。ワイルドカードだけは展開されうるので、
気になる場合は `set -f` を併用する。

`git add` 側も同様に `env:` へ移すと揃う。

### 背景

Mantis（Google の AI セキュリティレビュー用ハーネス）の採用検討中に、
リポジトリを読んでいて見つかったもの。Mantis 自体は不採用
（`docs/handover.md` の「検討して見送った技術」参照）。
