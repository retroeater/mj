# 新サイト 設計メモ

現行サイト（Cloudflare Workersで配信中の`cloudflare`ブランチ。
`gh-pages`は切り戻し用に残しているだけで配信には使っていない）とは
別に、同等のコンテンツを新規構築するための設計方針。

**現在の状況**: 検討を一旦中断している。
先に現行サイトの改善とサーバー移行（Cloudflareへのドメイン切替）を済ませてから、
新規構築にじっくり取り組む方針。再開するときは「11. 再開の手引き」から読むとよい。

ただし、移行や改善を進める際も**その先に新規構築があることを踏まえて**判断すること。

---

## 1. 位置づけ

### なぜ「移行」ではなく「新規構築」か

当初は Cloudflare への単純移行を進めていたが、次のようなことをやりたいと考えるようになったため、
既存コードの改修ではなく新規構築に切り替えた。

- ユーザーIDの発行と、それに紐づくサービス提供
- トレーディングゲームのような機能
- Google Charts では表現しきれない可視化
- 表形式中心の構成から、モダンでインタラクティブな画面へ

既存27ページの互換性を保ちながらこれらを載せるより、作り直した方が早い。

### 現行サイトの扱い

**そのまま動かし続ける。** ただし「現行サイト」の内訳は一様ではない。

- 配信中の`cloudflare`ブランチは、14ページがビルド時生成に移行済み
  （#7）。これらはスプレッドシートを更新しただけでは反映されず、
  `regenerate-page.yml`を`workflow_dispatch`で手動実行するか、
  スクリプト側の変更をpushする必要がある。定期実行（週次など）を
  設けるかどうかは#103で判断中
- 残り8ページ（型B/C/ランキング系）は Google Charts 方式のままで、
  訪問者がページを開くたびにスプレッドシートを読みに行く。
  この8ページに限れば、スプレッドシートを更新するだけでデータが
  反映される
- `gh-pages`ブランチ（切り戻し用、配信には使っていない）は
  27ページ全部がGoogle Charts方式のまま凍結されている。
  **「触らず放置してもデータだけは最新」は`gh-pages`にしか
  当てはまらない。**

これまで「Google Charts依存」は欠点として扱ってきたが、`gh-pages`の
ように凍結して運用する局面では、触らずに放置してもデータだけは
最新という利点になる。ただし配信中の`cloudflare`ブランチの
生成済み14ページはこの利点を持たない点に注意すること。

### 公開の仕方

一気にリニューアルした形で公開したい。段階的に置き換えるのではなく、
新サイトが揃った時点でドメインを切り替える。

第1弾で公開するもの:

- 選手データベース
- 鳳凰戦・女流桜花のランキングおよび成績詳細

### 着手順序: 最初に作るのは index.html（トップページ）

上記の公開スコープとは別に、**Astroでの試作・着手対象**は
index.html（トップページ）とする（#20をクローズし変更）。

理由:

- 他26ページと構造が独立しており（#15）、依存が最も少ない
- 現行サイトのindex.htmlはiPortfolioテンプレート由来で、
  作り直しが必要（別issue #101）。試作と作り直しを同時に進められる
- 選手データベース等の他ページは #7（Google Charts依存の解消）・
  #95（テーブル描画方式の比較検討）で現行サイト側の方式を
  先に固める必要があり、この段階でAstroを持ち込むと変数が増えすぎる

トップページの位置づけは**個人の実績を見せる場**。
選手データベースは平野良栄個人のポートフォリオを構成する
要素の一つという整理（詳細は #15 / #101）。

なお「帰り道」ページ（video_wayhome.html）の動画中心デザインへの
作り変えは、現行サイト側のページとして実施した（#7完了後、別issue
#102）。**2026-09-12、#102第2段をこの新サイト設計の先取りパイロットと
して位置づけることにした。** ページ自体は現行サイト（Astroではなく
Python生成）のままだが、カラートークン・ダークモード・共有ボタン・
構造化データなど、この先新サイトで必要になる判断・部品を先に試し、
持ち越せるものをここに記録している。詳細は「12. パイロット:
video_wayhome」参照。

## 2. デザイン方針

### トーン

**静か。** 白基調、余白を多めに、装飾を削ぎ落とす。
濃色・高コントラスト・動きの多い方向（スポーツ中継のグラフィックのような）ではない。

**ただし動画セクションは濃色固定とする例外を置く**（2026-09-12決定。
経緯は §12 パイロット: video_wayhome）。サイト全体のトーンは上記のまま
維持し、動画（`video_wayhome` 系）だけを OS のカラーモード設定に関係なく
常に濃色で表示する。写真・サムネイルが主役になる画面では濃色の方が
素材が立つため。**例外はこの1系統に限る**（表・選手データベース側へ
広げない）。

**この例外は配色に限る。動き（自動再生・アニメーション）には及ばない。**
2026-09-12、video_wayhome の背景動画自動再生（#102第3段）を見送った際、
この線引きを理由の一つとした。「動画セクションは例外」とだけ書くと
新サイト着手時に動きの追加まで例外の範囲と読まれうるため、明示的に
分けて記録する。経緯は §12 参照。

**ダークモードに対応する。** 後から足すと全画面を見直すことになるため、
最初から両モードで色を決める。「静か」なトーンは装飾が少ないぶん、
色を二重に管理する対象が減るので相性が良い。

### 選手一覧は表形式を維持する

カードグリッドにはしない。理由は写真の制約にある。

このサイトは連盟の公式サイトではないため、**公式の宣材写真が使えない**。
現行サイトと同様、X等のプロフィール画像を代替として使うことになるが、これらは

- 選手ごとに構図も画質もばらばら
- 本人が変更すれば変わる（だから週次の同期監視を作った）

写真に依存した設計は見た目が揃わず壊れやすい。
**小さめのアバターとして扱い、主役にはしない。**

そのうえで、表の見た目と操作性を洗練させる方向で作る。

### スパークラインは使わない

順位表の各行に小さな折れ線を埋め込む案は検討したが、好みに合わないため不採用。
リーグ内の成績推移は、独立した大きなグラフとして作る。

## 3. 画面構成

| 画面 | 見せ方 | 備考 |
|---|---|---|
| 選手データベース | 表。検索・絞り込みを上部に | 写真は小さいアバター |
| 選手個別ページ | レーダーチャート + リーグ遍歴 + 成績詳細 | 新規。現在は選手ごとのページがない |
| リーグ順位表 | 表 | |
| 期・リーグごとの成績推移 | **大きな折れ線グラフ** | **新規。現在は存在しない画面** |
| リーグ遍歴 | 帯・時系列 | 現行の `houou_leagues.html` に相当 |

### 一度に描画する行数を抑える

現行サイトでINPを測定したところ、ソート操作で458msかかっていた
（良好とされる200msの2倍以上）。内訳は描画443ms・JSの処理0.0msで、
JavaScriptではなく1102行すべてを描画し直すことがボトルネックだった。

DOM操作の方法を2通り試したが（DocumentFragment / replaceChild）、
いずれも改善しなかった。content-visibility: auto はスクロール時には
効くが、DOM順序が入れ替わる場面では効果がない。

新サイトでは、五十音タブ（#24）で表示件数を絞る。
「か行」なら100〜150行程度になり、この問題は自然に解消する。

**仮想スクロールは採用しない。** DOMに存在しない行は Ctrl+F の
ページ内検索で見つけられなくなるため。印刷やコピーにも影響し、
UIとしても好ましくないという判断。

### 選手個別ページを作る理由

現在は選手ごとのページがなく、表の行がすべて。個別ページを作れば

- 成績推移・レーダーチャート・リーグ遍歴・SNSリンクを1画面にまとめられる
- 検索エンジンから見て 1,000ページ超の入口ができる（SEO上の効果が大きい）

**この判断は実データで裏付けられている。** 2026年9月時点の Search Console のデータでは、
検索結果に表示された22URLのうち **14件が `?name=` 付きのURL** だった。

```
/houou_results.html?name=元氏なづは
/jpml_pros.html?name=白銀紗希
/houou_leagues.html?name=野村駿
/jpml_titles.html?name=樫林愛子
```

つまり**訪問者は特定の選手を探して来ている。**
いまはパラメータ付きURLで代用しているが、`/players/白銀紗希` のような専用ページがあれば、
検索順位もクリック率も上がる余地がある。

### 共有しやすくする

選手個別ページには、URLをコピーするボタンを置きたい。
検索流入の大半が特定の選手を見に来ていることから、
選手本人やファンがSNSで共有する場面が想定される。

navigator.clipboard.writeText() で実装でき、
外部ライブラリもSNSの公式ボタンも不要。
外部ドメインを増やさない方針とも矛盾しない。

### タイトルの重要性

同じ Search Console のデータで、**表示48回に対してクリックは2回**（CTR 約4%）だった。
掲載順位は1〜12位と悪くないのに、ほとんどクリックされていない。

原因は `<title>` だと考えられる。検索結果に「プロ」「成績詳細」「リンク」といった
素っ気ない文字列が並び、しかも「成績詳細」は4ページで重複している。

**新サイトでは、ページごとに内容が分かるタイトルを最初から設計すること。**
選手個別ページなら「白銀紗希 | 成績・プロフィール | ryoei.pro」のように、
検索した人が探しているものだと分かる形にする。

### リーグ内成績推移のグラフ（40人）

1リーグ40人前後の推移を1枚のグラフに描くと線が錯綜する。
**全員を薄いグレーで描き、選択した1人だけ色を付けて前面に出す**方式を採る
（focus + context と呼ばれる手法）。

順位表の中には埋め込まず、独立した画面として作る。

## 4. レーダーチャート

### 使う指標

現行の `league_ranking.js` に、すでに8部門の集計ロジックが実装されている。
独自に指標を考案する必要はなく、この中から性格の異なるものを選ぶ。

| 軸 | 元になる部門 | 表すもの |
|---|---|---|
| 実績 | 通算得点 | どれだけ積み上げたか |
| 効率 | 通算得点/期 | 1期あたりの強さ |
| 安定性 | 期単位浮き率 | 大崩れしないか |
| 継続力 | 期連続浮き回数 | 好調を持続できるか |
| 爆発力 | 節最高得点 | 一撃の大きさ |
| 上昇力 | 連続昇級回数 | 上のリーグを目指す勢い |

「節単位浮き率」は「期単位浮き率」と、「節連続浮き回数」は「期連続浮き回数」と
性質が近いため軸からは外した（ランキングページには引き続き残す）。

### 尺度を揃える

通算得点（数千点規模）と連続昇級回数（数回規模）では桁が違うため、そのままでは同じ図に描けない。
**全選手中の順位をパーセンタイルに変換して 0〜100 に揃える。**

「通算得点で上位5%、爆発力で上位20%」という読み方になる。

### 表示上の注意

レーダーチャートは面積が誤解を生みやすく、軸の並び順で印象が変わるという批判がある。
読み物としては面白いので採用するが、
**「公式な評価ではなく、全選手内での相対的な位置を独自に算出したもの」と画面上に明示する。**

### 牌譜データは使わない

和了率・放銃率・立直率といった麻雀本来の指標は、牌譜がないと計算できない。
動画等から牌譜に起こす作業が現実的でないため、少なくとも当初は提供しない。

## 5. 技術選定

| レイヤー | 選定 | 理由 |
|---|---|---|
| フレームワーク | **Astro**（Cloudflare アダプタ） | 静的ページと動的APIを同居できる。将来ログインが必要になっても、そのまま拡張できる |
| データベース | **Cloudflare D1** | 同一プラットフォーム。無料枠で足り、自動停止もない |
| 可視化 | **Apache ECharts** | Google Charts より表現力が高く、無料。focus + context もレーダーチャートも扱える |
| UI | 未定 | インタラクティブな部分に island が必要になったら選ぶ |

### 却下した選択肢

同じ検討を繰り返さないために記録しておく。

- **Supabase** — 無料枠は1週間アクセスがないとプロジェクトが自動停止する。
  選手が月に数回しか使わない用途では実質的に使えない
- **microCMS** — メンバー数が有料の Team プランでも3人（追加は1人1,200円/月）。
  スプレッドシートを置き換える必然性もない
- **PostHog** — Cloudflare Web Analytics で足りている。JSと外部ドメインが増える
- **Upstash / Pinecone / Stripe** — 該当する用途がない
- **全属性のKey-Value化（EAV）** — 型も制約も失われ、
  「中田花奈の行に `HTTP 404` が入る」ような事故を防げなくなる。
  列の追加は `ALTER TABLE` 一行で済むので、柔軟性のために構造を捨てる理由がない

### 検討対象の技術

- **React.js / Next.js** — 新規構築時に検討。現行サイトには過剰であり、
  ビルド工程を前提とするため見送った
- **Lit** — 同上
- **Tailwind CSS** — 同上。加えて現行の Bootstrap と役割が重複する
- **デジタル庁 デザインシステム** — 新規構築時に検討。Bootstrapからの
  全面的な載せ替えになるため現行サイトでは非現実的だが、
  公的性格の団体のサイトという位置づけには合う
- **SPA化** — 却下。訪問者はGoogleから `?name=` 付きの個別URLに
  直接到達しており、URL単位の流入がこのサイトの生命線である。
  新規構築時も、この性質は前提として維持すること

## 6. データベース設計

### 現状の問題

スプレッドシートは5冊に分かれ、ページごとに別々のシートを読んでいる。
そのまま D1 のテーブルに移すと、構造の悪さまで引き継ぐことになる。

実害も出ている。中田花奈の行に `HTTP 404` という文字列が入り、画像が壊れた。
CSVの備考列が転記時に紛れ込んだもので、**型もスキーマもないから起きた事故**だった。

### 設計方針（4つの改善）

**1. 鳳凰戦と女流桜花を1つのテーブルにまとめる**

両者は構造が完全に同じ。別テーブルにすると集計SQLが2本になり、
将来「最強戦」「WRC」を足すたびにテーブルが増える。
`competition_id` を1列持たせるだけで解決する。

**2. 節ごとの点数を縦持ちにする**

現在は `第1節`〜`第13節` が13列並ぶ横持ち。1行1節に正規化する。
ランキングの集計が劇的に簡単になる。

| 部門 | 横持ち | 縦持ち |
|---|---|---|
| 節最高得点 | 13列を比較 | `MAX(score)` |
| 節単位浮き率 | 13列をループ | `AVG(score > 0)` |
| 節連続浮き回数 | 自前で走査 | ウィンドウ関数 |

`league_ranking.js` が数百行かけている処理の多くがSQL数行で書ける。
節数がリーグや年代で違っても対応できる。

**3. 選手を名前ではなくIDで繋ぐ**

改名は年数件のペースで発生している。現在は改名を検知するたびに、
過去の成績データを新名前で全シート横断で上書きする運用。

IDで繋げば `players.name` を1箇所書き換えるだけで済む。**運用の手間が確実に減る。**

**4. リーグに序列を持たせる**

`A1 > A2 > B1 ...` の順序が文字列でしか表現されていない。
`jpml_pros.js` には「鳳凰位を `00` に置き換えてソートする」という工夫が入っていたが、
本来データ側で持つべきもの。序列を数値で持てば昇級・降級が引き算で判定できる。

なおスプレッドシートに「リーグ」シートがあり、A1=1、A2=2 … E3=13 とマッピング済み。
これをそのまま `rank_order` に使える。

### スキーマ

```sql
CREATE TABLE players (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  name_kana   TEXT,
  name_en     TEXT,
  office      TEXT,      -- 所属
  hometown    TEXT,      -- 出身地
  ron2_id     TEXT,      -- 龍龍ID。引退者や未登録者はNULL
  image_url   TEXT
  -- 誕生日などは必要になった時点で ALTER TABLE で追加する
);

CREATE TABLE player_names (   -- 旧名。旧名でも検索できるようにするためのもの
  player_id   INTEGER NOT NULL REFERENCES players(id),
  former_name TEXT NOT NULL
);

CREATE TABLE competitions (
  id     INTEGER PRIMARY KEY,
  name   TEXT NOT NULL,   -- 鳳凰戦 / 女流桜花
  gender TEXT             -- 女流桜花は女性限定
);

CREATE TABLE leagues (
  id             INTEGER PRIMARY KEY,
  competition_id INTEGER NOT NULL REFERENCES competitions(id),
  name           TEXT NOT NULL,     -- A1, A2, B1 ... E3
  rank_order     INTEGER NOT NULL,  -- 小さいほど上位。鳳凰位=0、A1=1 … E3=13
  has_half       INTEGER NOT NULL   -- 前後期の有無
);

CREATE TABLE season_results (
  id             INTEGER PRIMARY KEY,
  player_id      INTEGER NOT NULL REFERENCES players(id),
  competition_id INTEGER NOT NULL REFERENCES competitions(id),
  league_id      INTEGER NOT NULL REFERENCES leagues(id),
  season         INTEGER NOT NULL,  -- 期
  half           TEXT,              -- 前期/後期。has_half=0 のリーグではNULL
  place          INTEGER,           -- 順位
  result         TEXT,              -- 昇級 / 降級 / 残留
  total_score    REAL
);

CREATE TABLE section_scores (
  result_id   INTEGER NOT NULL REFERENCES season_results(id),
  section_no  INTEGER NOT NULL,   -- 節番号
  score       REAL NOT NULL,
  PRIMARY KEY (result_id, section_no)
);

CREATE TABLE player_links (   -- X・note・YouTube・龍龍。サービス追加が列追加にならないよう縦持ち
  player_id INTEGER NOT NULL REFERENCES players(id),
  service   TEXT NOT NULL,   -- ron2 / x / note / youtube
  handle    TEXT,
  image_url TEXT,
  PRIMARY KEY (player_id, service)
);
```

### 前後期の扱い

前後期の有無はリーグによって違う。

| 対象 | 前後期 |
|---|---|
| 女流桜花 全リーグ | なし（通期） |
| 鳳凰戦 A1・A2 | なし（通期） |
| 鳳凰戦 B1以下 | あり |

`season_results.half` に直接持たせると、A1の行では常にNULLになり
「なぜここだけNULLなのか」が後から分からなくなる。
`leagues.has_half` として定義側に置くことで、NULLの理由がデータから読み取れる。

制度変更（例: A2も前後期制にする）があっても、その行の `has_half` を変えるだけで済む。

### 件数の目安

| テーブル | 件数 |
|---|---|
| `players` | 約1,100 |
| `season_results` | 数万 |
| `section_scores` | 数十万 |
| `player_links` | 約2,000 |

`section_scores` が数十万行になるが、D1の無料枠は1日500万行の読み取りなので余裕がある。

### 移行時に行いたい検査

改名はすべてを把握する方法がないため、移行スクリプトに検出処理を組み込む。

## 12. パイロット: video_wayhome（2026-09-12、#102第2段）

video_wayhome.html を「新サイトの先取りパイロット」として全面的に
作り変えた（表形式 → 全画面ヒーロー + 横スクロールのエピソード列）。
全27ページの中で最も影響が小さいページという判断で選んだ。現行サイトの
「作り込みすぎない」方針は、このページとこのページ専用のCSS/JS
（`style.css`末尾の`.mj-video-*`ブロック、`video_wayhome.js`）に限り
今回だけ踏み越えている。実装は`scripts/generate_video_wayhome.py`
（`lib/page.py`の`render_content()`を使用。表を前提とした
`TableConfig`/`render()`はこのページではもう使わない）。

成果物は見た目そのものより、以下の「新サイトへ持ち越せる判断と部品」。

### カラートークン

背景・面・前景・弱い前景・境界・強調・強調の上に乗る文字色の
7トークンで開始した（新サイトの「静か」なトーンなら色数は
増やしすぎない方がよいという設計方針そのままの粒度）。

```css
--mj-v-bg          /* 背景 */
--mj-v-surface     /* 面(カード・パネル) */
--mj-v-fg          /* 前景(本文) */
--mj-v-fg-muted    /* 弱い前景(補足テキスト) */
--mj-v-border      /* 境界 */
--mj-v-accent      /* 強調(リンク・フォーカスリング等) */
--mj-v-accent-fg   /* 強調の上に乗る文字色 */
```

- ライト: bg `#ffffff` / surface `#f5f5f5` / fg `#1a1a1a` / fg-muted
  `#5f6368` / border `#dcdcdc` / accent `#2f5d78` / accent-fg `#ffffff`
- ダーク: bg `#121212` / surface `#1e1e1e` / fg `#f5f5f5` / fg-muted
  `#a8adb3` / border `#3a3a3a` / accent `#7fb3d5` / accent-fg `#0d1b24`
- 配色はWCAG AA（本文4.5:1、大きい文字3:1）を満たすよう事前に
  相対輝度から計算して選定し（境界色は装飾のため対象外）、実装後に
  Lighthouse accessibilityでも実測して確認した（下記参照）。border以外の
  組み合わせはすべて4.5:1以上
- 命名は`--mj-v-`プレフィックス（`v`=video、他ページの`.mj-*`と衝突しない
  ための仮の区別）。新サイトへ持ち越す際は接頭辞を外す・全ページ共通の
  トークンとして再設計する、のどちらかを検討すること。粒度・命名の
  考え方（機能で名付ける、色名や見た目で名付けない）はそのまま使える
- 適用範囲は`body:has(.mj-video-page) { ... }`で限定した。`body`要素自体に
  クラスを持たせる手段が`lib/page.py`のテンプレートに無いため、
  既存の`body:has(.mj-table)`と同じ子孫セレクタの流儀に合わせている

### Bootstrap 5.3のカラーモード（data-bs-theme）は採用しなかった

検証はした。`assets/vendor/bootstrap/css/bootstrap.min.css`には
`[data-bs-theme=dark]`のCSS変数上書きが実際に含まれており、機構自体は
利用可能だった。そのうえで採用しなかった理由:

- Bootstrapは`prefers-color-scheme`を自動で見ない。`data-bs-theme`属性を
  JS（`matchMedia`）で能動的に付け外しする必要があり、それなら最初から
  CSSの`@media (prefers-color-scheme: dark)`だけで完結する今回の方式の方が
  JSが1本減る
- このページがBootstrapコンポーネントに依存しているのは実質ナビバーのみで、
  そのナビバー（`navbar.js`）は`navbar-dark bg-dark`が常時ハードコードされ
  ており、ページのテーマに関係なく常に暗い配色。`data-bs-theme`を切り替えても
  ナビバー自体の見た目は変わらない（触っても得るものが無い）
- `data-bs-theme`は`<body>`に置けばこのページだけに閉じられることは確認した
  （`<html>`に置く必要はない）が、独自トークン（`--mj-v-*`）とBootstrap変数
  （`--bs-*`）の二重管理になるだけで、今回のボタン・カード等は全て独自クラス
  でありBootstrapの`--bs-*`変数を参照していないため、乗せる実益が無かった

新サイトでBootstrap依存度が今より高くなる場合（フォーム・アラート等を
多用する場合）は、改めて`data-bs-theme`ベースへの統合を検討する価値がある。

### トーン: 実装して分かったこと（判断材料。結論はここでは出さない）

`docs/new-site-design.md`のトーン記述は「静か。白基調、余白を多めに、
装飾を削ぎ落とす。濃色・高コントラスト・動きの多い方向ではない」。
今回の全画面ヒーローは動画配信サービス的な構成で、正面からぶつかる。
実装して分かった点を判断材料として記録する。

- **ヒーロー内のテキストは、ページのカラートークンと独立させ常に明色
  （白系）で固定した。** 理由は任意の写真（選手ごとに構図も色味も
  バラバラなサムネイル）の上に文字を置く可読性確保で、暗いグラデーション
  スクリム（`linear-gradient`、常に黒系・不透明度を段階的に上げる)を
  敷いている。トークンを二重管理しているわけではなく、「写真の上に
  文字を置く」という別の要請に対する処理という整理だが、**この整理が
  トーン記述（色を二重に管理する対象を減らす）と厳密に両立するかは
  意見が分かれうる。** ヒーロー以外（エピソードカード列・検索欄）は
  トークンで完全にライト/ダーク切り替わる
- **ダークモードは「シネマティックに寄る」というより、単に反転した配色
  になった。** ヒーロー自体が常に暗いスクリム+写真なので、視覚的な
  差はエピソードカード列から下（白背景⇔黒背景）にしか出ない。写真が
  主役の構成では、そもそもページの明暗の影響範囲が限定的という発見
- **選手の顔写真が大きく前面に出る構成は、「小さめのアバターとして
  扱い主役にはしない」という選手データベースの方針（3章）と対照的。**
  video_wayhomeは動画の見せ方の話であり選手データベースの一覧設計とは
  別物だが、同じサイト内で「写真を主役にする画面」と「写真を脇役にする
  画面」が両方存在することになる。使い分けの基準を明文化するかどうかは
  検討の余地がある
- 装飾（角丸・影・グラデーション）は最小限に留めた（スクリム以外に
  box-shadow等は使っていない）。この点は「装飾を削ぎ落とす」というトーンと
  矛盾しない

**結論: (b)「動画セクションだけ例外にする」を採用した（2026-09-12決定）。**
新サイト全体のトーン（静か・白基調）はそのまま維持し、動画セクションだけを
濃色の例外とする。§2「デザイン方針 > トーン」にも同じ決定を記載してある
（§12だけに書くと、新サイト着手時に §2 だけ読んで矛盾するため両方に置く）。

実装は「OSの設定に関係なく常に濃色」。`@media (prefers-color-scheme: dark)`
による上書きをやめ、ダーク側の値を `body:has(.mj-video-page)` の既定として
直接持たせた。上の「ライト/ダークで切り替わる」という記述のうち、
エピソードカード列・検索欄がライトになる経路は無くなっている。

- **トークンの構造（機能名の7つ）は両モード前提のまま残した。** 値の組を
  差し替えれば両モードに戻せる形を崩していない。新サイトへ持ち越す資産は
  トークンの粒度と命名であって、このページの配色値ではないため
- **消したライト側の値はこのドキュメント（上の「カラートークン」節の表）に
  残してある。** CSS側にコメントで複製すると二重管理になるので複製しない
- **`color-scheme: dark` を併せて指定した。** 指定しないと、OSがライト設定の
  利用者で `#searchBoxes` の入力欄・スクロールバー・フォーカスリングなどの
  UA既定スタイルが明色のまま浮く。ビューポートのスクロールバーは
  ルート要素の `color-scheme` で決まるため `html:has(.mj-video-page)` に
  置いた（`body:has()` と同じ `:has()` スコープなので他26ページには及ばない）
- 配色値はダーク側をそのまま採用しており変更していない。ただし固定化に
  よって**これまで計測できていなかった2件のコントラスト不足が顕在化した**
  （下記）。トークンの値そのものは変えていない

**固定化で顕在化したコントラスト不足（2件、同時に修正した）**

Lighthouse（headless Chrome）は `prefers-color-scheme` を指定せず常に
ライト側で走るため、これまでこのページの**ダーク側の配色は一度も
Lighthouse で計測されていなかった**。濃色固定にしたことで初めて計測対象に
なり、`color-contrast` が2件失敗した（accessibility 0.96 → 0.92）。
いずれも配色値の問題ではなく、ダーク側でしか踏まない別の不具合だった。

1. **ヒーローのボタンが強調色の文字になっていた（詳細度の取り違え）。**
   `.mj-video-page a`（詳細度 0,1,1）が `.mj-video-btn-primary`（0,1,0）に
   勝つため、白背景の「再生」ボタンの文字が `--mj-v-accent` になっていた。
   ダーク側の accent `#7fb3d5` × 白背景で **2.26:1**（AA 不合格）。ライト側の
   accent `#2f5d78` なら 7.0:1 で通っていたため、ライトでしか計測して
   いなかった間は表面化しなかった。`a:not(.mj-video-btn)` に変えてボタンを
   除外し、`#1a1a1a` × 白 = **17.4:1** に戻した。副ボタン（写真の上）も
   同じ理由で accent になっていたが、背景が画像のため axe は評価できず
   指摘されていなかった。こちらも `#ffffff` に戻っている
2. **`.mj-lead`（#158 の説明文）が明色前提のままだった。** 全ページ共通の
   `.mj-lead` は `color: #555555` / `border-top: #e5e5e5` をベタ書きしており、
   `#121212` の上で **2.51:1**（AA 不合格）。`body:has(.mj-video-page)` 側で
   `--mj-v-fg-muted` / `--mj-v-border` に差し替え、**8.29:1** にした

**教訓**: ダークモードを `prefers-color-scheme` でしか持たないページは、
Lighthouse/axe の自動計測がライト側しか見ない。**両モードを持つページでは、
計測時に配色モードを明示して両方測らないと片側が検証されないまま残る**。
新サイトで両モードを持つなら、計測手順に「両モードで測る」を明記すること。

確認結果（Chromium、OSをライト設定に相当する `colorScheme: 'light'` で検証）:

- video_wayhome: `html`/`body` とも `color-scheme: dark`、body背景 `#121212`、
  `#searchBoxes` `#1e1e1e`、`.mj-filter-input` `#121212`。明色の浮きは無し。
  上記2件の修正後、Lighthouse mobile の `color-contrast` は合格
  （accessibility 0.96、残る指摘は `link-name` のみ）
- 他26ページ: ライト設定・ダーク設定のいずれでも body背景 `#ffffff`、
  `color-scheme` は `normal` のまま。従来どおり白基調で変化なし
- **白いページからの遷移**: 白基調のページ（`video_mtsuku.html`）から
  このページへ遷移した直後のフレームを撮って確認したが、白の
  フラッシュは観測されなかった。`color-scheme: dark` により最初の描画前から
  キャンバスが濃色になるため。ナビバーは全27ページ共通で `bg-dark`
  （常に暗色）なので画面上端の帯は遷移前後で連続しており、切り替わるのは
  その下の本文領域だけ。**所見として許容範囲**（対策はしない）

### `<meta name="theme-color">` は入れない（2026-09-12判断）

濃色固定にしたことで、モバイルブラウザのUI（アドレスバー）だけが明色のまま
残る。`extra_head` 経由でこのページにだけ `theme-color` を入れる案を検討したが、
**入れないことにした**。理由:

- ナビバーは全27ページ共通で `bg-dark`。つまり画面上端に接する色は全ページ
  同じで、`theme-color` が要るなら27ページ全体で入れるべき性質のもの。
  1ページだけに入れると、ページ間を移動するたびにアドレスバーの色が
  変わる不整合が出る
- 全ページに入れるには `HEAD_TEMPLATE` の変更が必要で、他26ページへ波及する。
  今回のスコープ（このページの配色固定）を超える
- 今回避けたかった「明色の浮き」（入力欄・スクロールバー・フォーカスリング）は
  `color-scheme: dark` で解決済み。`theme-color` はページ外のブラウザUIの話で
  別問題

サイト全体の `theme-color`（ナビバーの `bg-dark` に合わせる）は、
`HEAD_TEMPLATE` を触る別の機会に検討する。

### 共有ボタン（URLコピー）

`navigator.clipboard.writeText()`を第一の手段とし、以下の順でフォール
バックする（`video_wayhome.js`）:

1. `navigator.clipboard`が利用可能（`window.isSecureContext`）→
   `writeText()`
2. 失敗、または非セキュアコンテキスト等で利用不可 → 非表示の
   `<textarea>`を生成し`document.execCommand('copy')`（レガシー手段。
   非推奨APIだが対応環境が広い）
3. それも失敗 → コピーはせず、URLをテキストとして
   `aria-live="polite"`の領域に表示し「手動でコピーしてください」と促す

コピー対象は固定URLではなく`location.href`（表示中のURL、`?name=`が
付いていればそれを含む）。成功・失敗いずれも`#copyStatus`
（`visually-hidden`+`aria-live="polite"`）でスクリーンリーダーに伝える。
この3段構えの方針は、新サイトの選手個別ページの共有ボタンにそのまま
持ち越せる。

### 構造化データ（#13先行実装）

`VideoObject`（最新話1件）と`ItemList`（エピソード全件、`ListItem`に
`position`/`url`/`name`）の2ブロックをJSON-LDで出力した
（`scripts/generate_video_wayhome.py`の`build_json_ld()`）。

- **検証方法について、当初の想定（Googleのリッチリザルトテストでの検証）
  を計画どおりには実行できなかった。** 同ツールはページの公開URLでの
  取得、またはHTMLコードの手動貼り付けを前提としており、(a)
  このページは本番未反映のためURLでの検証ができず、(b)
  貼り付け操作を自動化で代行することは、対話的な利用を前提とした
  外部ツールへの想定外のアクセスになりうると判断し見送った。
  代わりに次の2点をこのセッション内で検証した: ①両JSON-LDブロックが
  構文的に有効なJSONであること（ブラウザ上で`JSON.parse`して確認）、
  ②schema.orgの`VideoObject`/`ItemList`が求める必須・推奨プロパティが
  揃っていること（`name`/`description`/`thumbnailUrl`/`uploadDate`、
  `contentUrl`・`embedUrl`）をコードレビューで確認。**本番反映後、
  実URLでリッチリザルトテストを改めて実行することを推奨する**
  （#13にも同じ内容を記録した）
- **`duration`（動画の長さ、ISO 8601形式）は設定していない。**
  スプレッドシートに秒数などの尺情報が無いため。Googleは`VideoObject`に
  `duration`を推奨プロパティとして挙げており、将来シート側に列を
  追加できるなら埋める余地がある（既知のギャップとして記録するのみで、
  本パイロットでは対応しない）
- `</script>`によるHTML側スクリプトタグの早期終了を防ぐため、
  JSONシリアライズ後に`"</"` → `"<\\/"`の置換を行っている
  （標準的な対策。値に選手名・タイトル戦名などユーザー入力に近い
  文字列を含むため）
- 新サイトの選手個別ページでも同様に`Person`/`VideoObject`等の
  JSON-LD出力が要る（#13本体のスコープ）。今回のビルダー関数の形
  （辞書を組み立てて`json.dumps` + エスケープ）はそのまま流用できる

### 新サイトへ持ち越せる部分／捨てる部分（#164の材料）

持ち越せる:

- カラートークンの粒度・命名の考え方（7トークンで始める、機能で
  名付ける）。具体的な配色値は新サイトのブランドで決め直す前提
- 共有ボタンの3段フォールバック方針（clipboard API →
  execCommand → 手動コピー案内）
- 構造化データのビルダー関数の形（辞書組み立て + `json.dumps` +
  `</`エスケープ）
- 横スクロール+`scroll-snap`のカード列パターン（スクロールバーを
  隠さない、矢印ボタンは`prefers-reduced-motion`で分岐）は、選手個別
  ページの「関連選手」「同期の成績」等の横並び表示にも使えそう
- WCAG AAの相対輝度計算による配色検証の手順（実装前に数値で
  確認してから実装する、実装後にLighthouseで裏取りする）

捨てる（このページ限りの判断で、新サイトでは別解が必要）:

- `--mj-v-`という接頭辞そのもの（1ページ専用の暫定名。新サイトは
  全ページ共通のトークン体系になるはずで、命名をやり直す）
- `body:has(.mj-video-page)`によるスコープの仕方（Astroならコンポーネント
  単位でCSSを閉じ込められるため、この子孫セレクタでのスコープ手法自体が
  不要になる）
- ヒーロー内テキストを常に固定色にする実装（写真主体の1画面限りの
  処理。選手個別ページのような「写真が脇役」の画面では素直にトークンで
  完結できるはず）
- `render_content()`を手で直接呼ぶ構成（新サイトはAstroのテンプレート/
  コンポーネントが担う領域で、Pythonの文字列組み立ては引き継がない）

### 第3段（背景動画の自動再生）は見送った（2026-09-12決定、#102）

パイロットの結論として、新サイトへ持ち越す判断に残す:

- 動画配信サービス風のレイアウトは、**静止画のヒーロー + 横スクロールの
  候補列までで成立する。自動再生の背景動画は無くても体験は損なわれない**
- 判断の決め手は見た目ではなく素材とパフォーマンス。「帰り道」は
  10〜30分のインタビュー動画で、動画配信サービスの背景動画に相当する
  数十秒のトレーラー素材が存在しない。ブラウザの制約上、自動再生は
  必ずミュートになるため、話している人が音無しで映り続けるだけの
  ループになってしまい回避できない。加えて mobile の LCP に余力が無い
  （第1段のヒーロー画像追加だけで 0.5〜0.7秒悪化した実績がある）。
  新サイトで動画を扱う画面を作る際も同じ制約がかかる
- トーンの例外（§2）は配色に限ることをこの見送りの理由の一つにした。
  自動再生の背景動画は装飾の中でも最も動きが大きい要素で、例外を
  色から動きへ広げると §2 の「動きの多い方向ではない」という記述が
  ほぼ無効になるため
- 理由の全文・将来「クリックで初めて埋め込みを読み込む」方式を検討する
  余地は #102 のクローズコメントに記録した
